# 行文风格
## 触发条件和适用边界
适用于说明性、设计性、技术性的文档：设计文档、方案、说明、评审意见、代码注释、提交信息。这类文档的读者要用它做判断，因此对准确性的要求高于对可读性的要求。
不适用于两类。以说服为目的的文体，如推广材料、提案、对外宣讲，这些文体需要考虑读者的接受意愿，力度本身是手段之一；以对话为内容的记录，如会议纪要、评审记录，它们保留原话，其中包括当时的语气。

## 文风
文风取自软件工程类书籍的通行写法，如 Clean Code、重构。特征是中性、准确、克制。
表述的力度不等于内容的说服力。一件事实的说服力来自它本身：来自数据、来自代码、来自可核验的现象。用修辞去加强它，读者收到的只是语气，不是信息。
读者读一份技术文档，是要据此做判断。他需要知道发生了什么、为什么、代价是什么。语气对这三件事都没有贡献。
因此写作时把力气放在把话说准上，不放在把话说重上。

以下四种做法的共同点是：让读者感到作者很有把握，而读者说不出他为什么有把握。
**术语堆砌。** 用一串看似专业的词替代一个需要展开的说明。这些词往往没有定义，或者被用在与它原本含义不符的地方。读者看了三遍，仍不知道具体指什么。判断方法：把术语换成日常说法，若这段话说不出更多内容，说明原本就没有内容。
**浅显类比。** 把陌生的东西比作读者熟悉的东西，让读者产生"懂了"的感觉，而实际上没有得到任何可操作的说明。类比传递的是情绪上的亲近，不是结构上的对应。判断方法：看完类比之后，读者能否说出原来的东西是怎么运作的。说不出，这个类比只在制造理解的错觉。
**对比句式。** "不是 A，而是 B"这类写法放大语气，同时隐藏了条件：在什么情况下 A 成立、什么情况下 B 成立。读者读到的是被强调的 B，而不是 A 与 B 的差别。判断方法：先确认 A 在文档里出现过。从未出现的 A 被否定，读者无从理解这个否定针对什么。
**升华式收尾。** 结尾用一句总结或勉励替代结论。结论应当在前文给出并被推导出来；如果读者读到这里还需要一句总结才算读懂，说明前文没有写清。

## markdown 的排版倾向
**密集排版。** 大章节之间留有空行，章节与它的正文之间没有空行，标题紧贴它下面的第一行。
正文中每一行之间没有空行，属于同一个段落的句子连续书写，一行结束直接换行写下一句。
只有描述不同内容时才另起一段，段与段之间留一个空行。
代码块前后各留一个空行，代码块内部按其自身语法的习惯排版，不受本条约束。
松散排布有三种表现，都应当避免：标题与正文之间空一行；列表项之间空一行；同一个段落里的每一句各占一段。

```markdown
- 功能跑通了，分层被改掉了，当时看不出来，改动多了才发现

- 为了拿到上层的一个数据，让底层直接引用上层的概念

## 层次划分

依赖方向唯一：上层可以依赖下层，下层不得依赖上层。
```

密排的同一段内容：

```markdown
- 功能跑通了，分层被改掉了，当时看不出来，改动多了才发现
- 为了拿到上层的一个数据，让底层直接引用上层的概念

## 层次划分
依赖方向唯一：上层可以依赖下层，下层不得依赖上层。
```

**分点。** 并列的内容用列表，不写成连续的散句。并列项前后一致，要么都是名词短语，要么都是完整句子。
列表项各自独立成行，项与项之间不空行。列表与其引导句相邻，不空行；列表之后若另起内容，空一行。

**注释。** 需要读者知道、但不属于正文的说明，写成 HTML 注释，放在它所说明的位置。
注释用于交代上下文，例如某项为何暂缺、某处为何如此处理。它不用于留给自己看的工作记录。

验证方式：逐份通读，找出不该出现空行的位置。判断的界线是这个空行是否隔开了不同的内容。空行两侧若在说同一件事，属于同一个段落，这个空行应当删除。
需要通读才能判断，不靠工具扫描。工具能查出标题之后的空行与列表项之间的空行，查不出两个段落是否在说同一件事。
